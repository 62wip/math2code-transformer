## Отчёт по Math2Code Transformer

В отчёте описаны реализация системы, архитектура модели и результаты экспериментов. Обучение проводилось на Kaggle. Данные, чекпоинты моделей и репозиторий передавались в среду через датасеты Kaggle. Ссылки на запуски приведены в соответствующих разделах.

### Реализация системы

#### Анализ данных, предобработка и токенизация

Датасет содержит примеры вида «математическая задача/вопрос → ответ в виде Python-кода». Первичный анализ представлен в [eda.ipynb](../notebooks/eda.ipynb). По его результатам в предобработку было включено удаление комментариев из кода.

Предобработка реализована в [data_processing/data_preprocessing.py](../lib/data_processing/data_preprocessing.py):

```text
отсекаем длинные примеры -> очищаем код от комментариев -> дедуплицируем по (задача, код) ->
-> бьем на train/val -> считаем выходные ответы для эталонных решений val ->
-> сохраняем сплиты на диск
```

В валидационную выборку выделено порядка 8 тысяч примеров, остальные данные оставлены для обучения. Эталонные решения валидационной выборки исполняются для получения числовых ответов, необходимых для расчёта pass@1.

Для токенизации выбран BPE с размером словаря 16384 токена. Вспомогательные функции обучения и применения токенайзера реализованы в [data_processing/tokenizer.py](../lib/data_processing/tokenizer.py). Токенизация и сохранение данных представлены в [tokenization.ipynb](../notebooks/tokenization.ipynb). Подготовленные данные загружены на Kaggle как приватный датасет. Размер словаря в экспериментах не менялся.

#### Инструменты для обучения и экспериментов

Для настройки экспериментов реализован класс `Experiment`. Он поддерживает создание эксперимента из конфигурации, загрузку весов и полноценное восстановление состояния обучения.

Для параллельного исполнения программ реализован `SolutionExecutor`. Пул потоков управляет вспомогательными процессами и очередью задач. Вспомогательный процесс запускает каждую программу в отдельном дочернем процессе, контролирует время исполнения и возвращает результат. Этот механизм используется для проверки программ и голосования при инференсе.

Шаблоны обучения, проверки инференса и генерации посылки находятся в [using_model_templates](../notebooks/using_model_templates).

#### Батчивание

Для последовательностей переменной длины реализован `CodeDataLoader` в [data_processing/batching.py](../lib/data_processing/batching.py). Примеры группируются по близким длинам вопроса и кода, чтобы сократить объём паддинга. Размер батча ограничивается бюджетом токенов: коротких примеров помещается больше, длинных — меньше. Последовательности дополняются до общей длины внутри батча, формируются маски паддинга. Между эпохами перемешиваются примеры внутри групп и порядок батчей. При распределённом обучении батчи разделяются между процессами; в экспериментах использовались две GPU.

#### Цикл обучения

Реализован цикл обучения с опциональной поддержкой AMP и DDP:

- Automatic Mixed Precision используется для вычислений в смешанной точности на GPU.
- Distributed Data Parallel используется для обучения на двух NVIDIA T4. На каждой GPU находится копия модели, обрабатывающая свою часть данных. Градиенты синхронизируются при `backward()`. Обмен метриками и числом токенов для нормировки loss реализован отдельно.

Предусмотрены режимы работы на CPU и GPU. Ускорение измерялось в [ноутбуке с бенчмарками](https://www.kaggle.com/code/wwip62/dp-mixed-prec-benchmarks):

| Режим | Скорость, целевых токенов/с | Время на 1 млн токенов | Ускорение относительно baseline |
|---|---:|---:|---:|
| Baseline: FP32, 1 GPU | 9 721 | 102,9 с | 1,00× |
| Только AMP, 1 GPU | 25 129 | 39,8 с | 2,59× |
| AMP + DDP, 2 GPU | 42 699 | 23,4 с | 4,39× |

Для запуска обучения через консоль реализована утилита [train_script.py](../utilities/train_script.py): создание эксперимента, загрузка весов и восстановление обучения. Поддерживаются логирование и отслеживание метрик через W&B.

#### Валидация и метрики

Эпоха разделяется на мини-эпохи по количеству обработанных обучающих примеров — обычно 100k или 200k. На границах мини-эпох выполняется валидация. Предусмотрены два режима: small с метриками по логитам и heavy с генерацией и исполнением программ. Размер валидационной подвыборки задаётся отдельно для каждого режима.

Реализованы следующие метрики:

- Легкие:
    - Train/Val Loss — средняя CrossEntropy по токенам без паддинга на train и val. Паддинг не учитывается.
    - Top 1/5 accuracy — как часто эталонный токен совпадает с самым вероятным предсказанием или попадает в топ-5. Паддинг не учитывается.
- Сложные:
    - pass@1 — главная метрика: доля задач, где выбранная программа при запуске возвращает правильный числовой ответ. Сравниваем с эталоном с погрешностью вычислений.
    - BLEU — насколько сгенерированный код похож на эталонный по совпадениям фрагментов текста. Скорее вспомогательная метрика, потому что одну задачу можно правильно решить разным кодом.
    - No EOS rate — доля генераций, которые закончились без токена конца последовательности.
    - Repetition rate — насколько модель повторяется: для каждой программы считаем долю повторных четверок токенов, затем усредняем по программам.
    - Syntax valid rate — доля программ без синтаксических ошибок.
    - Numeric return rate — доля программ, у которых `solve()` отработал и вернул конечное число. Правильность ответа тут не проверяется.
    - Timeout rate — доля программ, которые не успели исполниться за заданный лимит времени (2 секунды).

Метрики реализованы в [utils/metric_calculation.py](../lib/utils/metric_calculation.py) и вызываются из [evaluation.py](../lib/evaluation.py).

#### Инференс и выбор ответа

Реализованы загрузка модели и токенайзера, greedy-генерация до `<eos>` или `max_new_tokens`, KV-кеширование и пакетный beam search с поддержанием ветвей поиска для всего батча. Первоначальные попытки реализации BeamSearchTopP были заменены на BeamSearchTopK.

Для выбора ответа используется исполнение K сгенерированных кандидатов и голосование по числовым результатам. Поддерживаются голосование по количеству совпавших ответов и голосование с весами по вероятностям кандидатов. Возвращается программа, соответствующая выбранному ответу.

Инференс организован следующим образом:

- Запросы группируются в батчи по длинам.
- Для каждого батча генерируются K лучей с переиспользованием KV-кешей.
- Кандидаты передаются пулу исполнения, после чего начинается генерация следующего батча.
- Готовые результаты собираются для голосования. Незавершённые задачи остаются в очереди ожидания; после генерации всех батчей собираются оставшиеся результаты.

Так исполнение программ на CPU перекрывается с генерацией на GPU. Отдельный замер ускорения от этого перекрытия не проводился.

### Архитектура модели и эксперименты

В качестве основы использовалась encoder–decoder архитектура Transformer. В ходе работы реализованы базовый вариант на блоках PyTorch и `Baseline++` с собственными блоками.

#### Исходный Baseline++

Сначала реализован `BaselineTransformerModel` на стандартных блоках PyTorch для проверки обучения. Затем реализован `BaselinePlusPlusModel`, ставший основой последующих экспериментов. Исходная конфигурация приведена в [baseline++.yaml](../experiment_configs/baselines/baseline++.yaml):

- 5 Encoder, 7 Decoder-блоков
- `embedding_dim = 512`,
- RoPE в качестве позиционированного кодирования
- FlashAttention, 8 голов
- Swish GLU 1024 в качестве FFN
- RMSNorm в качестве нормализации
- 1 MLP-слой `512 -> 16384` — размер словаря

Исходная модель обучалась около 8 часов без AMP и DDP и обработала около 15.2 млн примеров, то есть примерно 1.5 эпохи. Результат на открытом тесте — `public_pass@1 = 73.75%`. [Запуск обучения](https://www.kaggle.com/code/wwip62/train-baseline-longer). Точные параметры генерации для этой посылки не сохранились.

#### Эксперименты

Эксперименты проводились при ограниченном временном бюджете. Конфигурации находятся в [experiment_configs](../experiment_configs): `/1_hour_exps`, `/lr_40m`.

##### Часовые эксперименты: `enc=7, dec=5`, `ffn_dim=1536`
Выполнены три запуска длительностью около часа:

- control
- `enc=7, dec=5`
- `ffn_dim=1536`
[Вот запуск](https://www.kaggle.com/code/wwip62/experiments-train-pilot-1h). Получились следующие итоги:

![Pass@1 в часовых экспериментах](src/pass@1_1h_1.png)
По метрикам получилось так:

- *Pass@1:* лучший результат у FFN 1536 — 53.71%, у контроля — 53.12%, у `enc=7, dec=5` — 52.34%. Разница небольшая: преимущество FFN над контролем — всего 3 задачи из 512.
- *Val loss:* к концу часа лучше у контроля — 0.3486 против 0.3550 у FFN и 0.3614 у `enc=7, dec=5`.
- *Top-1 / Top-5 accuracy:* контроль и FFN практически одинаковые — 90.38% / 98.23% и 90.34% / 98.22%. У `enc=7, dec=5` чуть ниже — 90.06% / 98.19%.
- *Скорость:* `enc=7, dec=5` успел обработать около 1.9 млн примеров, контроль — 1.75 млн, FFN — 1.61 млн. Более широкий FFN оказался медленнее, но показал чуть лучший pass@1.
- *Стабильность:* loss в целом снижался у всех, а pass@1 колебался.

По одному часовому запуску уверенно назвать какой-то вариант стабильнее нельзя.

Для дальнейших экспериментов выбран FFN-1536: он показал немного более высокий pass@1, хотя устойчивое преимущество по совокупности метрик не установлено.

##### LR = 1.5e-4, 3e-4, 6e-4

Для сравнения learning rate использовались значения `1.5e-4`, `3e-4` и `6e-4`. Новые запуски ограничивались 40 минутами. Вот [запуск](https://www.kaggle.com/code/wwip62/experiments-train-lr-40min). Итоги:

![Pass@1 при разных learning rate](src/pass@1_40m_lr.png)

*В качестве LR=3e-4 был взят ffn1536 — там использовался именно такой lr.*

`1.5e-4` оказался слишком медленным для такого бюджета: к концу запуска pass@1 всего 42.97%. `6e-4` быстрее повышает pass@1 на старте, но потом преимущество перед `3e-4` пропадает, и кривые идут примерно рядом, местами обгоняя друг друга. У `6e-4` итоговый pass@1 — 48.24%, но устойчивого отрыва на общем участке времени не видно. Для дальнейшего обучения оставлен `3e-4`: короткие эксперименты не показали устойчивого преимущества от его изменения.


##### GQA и QK-Norm

Отдельно проверялись GQA — Grouped Query Attention с двумя KV-головами — и QK-Norm, нормирующий Q и K. [Вот запуск](https://www.kaggle.com/code/wwip62/train-experiments-1h-part-2-gqa-qk-norm
), вот результаты:

![Pass@1 в экспериментах с GQA и QK-Norm](src/pass@1_1h_2.png)

По итогу получилось так:

- *Pass@1:* лучший результат у QK-Norm — 54.49%, у FFN-1536 — 53.71%, у GQA — 52.73%. Но к концу запуска QK-Norm откатился до 51.95%, а GQA — до 50.78%. Уверенного победителя опять нет.
- *Val loss:* в конце у QK-Norm — 0.3641, у GQA — 0.3666, у FFN-1536 — 0.3550. По времени базовый вариант пока выглядит лучше.
- *Скорость:* за час GQA обработал около 1.45 млн примеров, QK-Norm — 1.35 млн, а FFN-1536 — 1.61 млн. То есть изменения замедлили обучение, и при одинаковом времени модели успели увидеть разное количество данных.

У реализации GQA было ограничение: в этом запуске он не попадал на быстрый бэкенд SDPA на T4. Позже быстрый бэкенд был включён через явное повторение K/V до числа Q-голов, что добавляет накладные расходы. Эти часовые результаты получены еще до исправления, поэтому они не отражают скорость исправленной реализации GQA.

Для дальнейшего сравнения выбраны два варианта: обычный MHA без GQA и QK-Norm и вариант с обеими модификациями. План состоял в сравнении через 5–8 часов и продолжении обучения выбранной модели.

**Итоговым решением стал Baseline++ с Multi-Head Attention, 6 encoder- и 7 decoder-блоками, без GQA и QK-Norm.**

#### Итоговые результаты

При подборе параметров инференса выбрано `beam_top_k=14`, с которым генерация укладывалась в 180 секунд. Чекпоинт `best` не улучшил результат baseline на открытом тесте. Для итоговой посылки использован `last`: **78.02%** public pass@1 и **73.62%** private pass@1. [Генерация посылки](https://www.kaggle.com/code/wwip62/generating-code-solution).

Повышение результата на открытой части теста не подтвердилось на закрытой части. Дальнейшая проверка архитектур потребовала бы большего бюджета экспериментов, а его не было.
